# 项目简介
本项目是一个基于 STM32F103C8T6 与 MPU6050 六轴传感器的端侧人工智能（TinyML）完整链路探索项目。
项目涵盖从底层高频数据采集、串口通信排错、Python 数据清洗与时序切分，到 Edge Impulse 模型训练。
在工程实践后期，为解决裸机架构下采集与处理的资源抢占问题顺便练习一下freertos，重构了基于 FreeRTOS 的多任务架构。

# 目的
本项目旨在探索 端侧人工智能（TinyML）在工业预测性维护（Predictive Maintenance）领域的微型化落地。核心目的是让低成本的微控制器（MCU）能够“听懂”机器的语言，自主分辨设备的“正常运转”与“异常故障”。
工业设备的“早期癌症筛查”：电机、风机、轴承等旋转机械在彻底损坏前，其振动频率与幅度通常会发生微妙变化。本项目通过采集 MPU6050 数据，训练模型区分 vibration（正常运转）与 sway（异常晃动/摩擦），模拟真实的工业故障诊断场景。一旦振动模式偏离正常基线，系统即可提前预警，避免突发停机造成的重大损失。
摆脱云端，实现真正的“本地诊断”：传统方案将数据传至云端分析，存在网络延迟且依赖通信。本方案尝试将 AI 模型直接部署在较为便宜的 STM32 芯片上，实现设备端侧的毫秒级实时判断，不仅节约了带宽成本，更保护了工业数据隐私。
极低成本的海量部署潜力：虽然 MCU 无法处理复杂的视觉 AI，但对于简单的振动时序分类任务却极其对口。在工业场景中，这意味着可以以极低的成本，在数百台电机上批量部署“智能听诊器”，实现状态监测的全面覆盖。

# 技术栈与工具
硬件平台：STM32F103C8T6 (Cortex-M3, 64KB Flash, 20KB RAM) + MPU6050
底层开发：C 语言, STM32 HAL 库, Keil MDK , FreeRTOS (CMSIS-RTOS v2)，cubeMX
数据处理：Python (自动化数据清洗与时序切分)
AI 平台：Edge Impulse (特征提取、模型训练、int8/float32 导出)

# 问题记录和经验积累
## 1. 裸机架构下的高频数据采集与串口乱码解决
初始架构：使用 TIM3 定时器配置为 10ms 中断（100Hz），在中断服务函数（ISR）中通过阻塞式 I2C 读取 MPU6050。
排错记录：初期在中断中直接调用自定义函数 uart_send_int 打印数据，导致出现大量 ♠HX)♣ 等乱码而且通过观察发现出现串口打印出现比较多个相同的数。
原因：串口发送耗时过长，导致中断频繁嵌套与状态机错乱。还有自定义函数uart_send_int的数组长度比较小。
解决方案：将串口打印逻辑移出中断，ISR 仅负责将数据存入全局二维数组 accel_buf，主循环检测到 window_ready 标志后再集中发送。同时扩大自写字符转换数组将12改为16，彻底消除乱码。
## 2. FreeRTOS 多任务架构重构
为解决主循环阻塞导致的潜在丢包问题，引入了 FreeRTOS 进行重构：
AcquireTask（采集处理任务）：优先级 AboveNormal，利用 osMessageQueueGet 阻塞等待数据。攒满 200 个点后集中处理。
InferTask（推理任务）：优先级 Normal，预留用于后续的模型推理。
数据流转：TIM3 中断中使用 osMessageQueuePut（超时设为 0）将 I2C 读到的原始数据压入队列，实现中断与任务的解耦。
## 3. 底层时基没有处理好，导致的系统死机
现象：系统在进入 FreeRTOS 调度前，死锁在 HAL 库的时钟初始化 while (__HAL_RCC_GET_FLAG(RCC_FLAG_HSERDY) == RESET) 循环中，且串口无任何打印。
原因：由于引入了 FreeRTOS，HAL 库的时基源从默认的 SysTick 切换到了 TIM2。在正常逻辑下，TIM2 每次触发中断，底层会自动调用 HAL_IncTick()，让系统的“毫秒计数器（uwTick）”加 1。
因为我的业务逻辑需要 TIM3 以 100Hz 的频率定时采集 MPU6050 数据（每 10ms 触发一次），所以我重写了 HAL_TIM_PeriodElapsedCallback 回调函数。结果导致 TIM2 和 TIM3 共用一个中断回调：TIM3 送来的是业务数据，TIM2 送来的是“系统心跳（+1ms）”。
但我的代码中只写了 if (htim == &htim3) 的分支，直接将 TIM2 的系统心跳请求忽略，未调用 HAL_IncTick()。
连锁反应：系统时间（uwTick）永远停止在 0，导致 HAL 库的所有超时机制全面瘫痪。HAL_Delay(100) 变成了无限死循环；卡死的地方（等待外部晶振起振）的“100ms 超时退出”逻辑也永远等不到，最终死死卡在那个 while 循环里出不来。
排查与解决：使用 Keil MDK 的 Debug 模式打断点，发现程序一直停留在 SystemClock_Config 等待晶振的循环中；随后通过串口收发实验排查了硬件无故障；仔细检查 CubeMX 配置确认时钟树无误，最终将嫌疑锁定在系统滴答定时器（Tick）未更新上。
修复：在中断回调的最前端拦截 TIM2 实例，补充调用 HAL_IncTick()，恢复系统心跳；同时，修正了外设初始化的顺序（将 HAL_TIM_Base_Start_IT(&htim3) 移动到 FreeRTOS 队列创建 MX_FREERTOS_Init() 之后），确保中断触发时队列句柄已经就绪，避免空指针崩溃。
## 4. Python 自动化数据清洗
在端侧 AI 的开发中，由于串口传输的物理特性，直接抓取下来的原始数据往往夹杂着乱码、丢包和不对齐的问题，无法直接用于云端训练。为此，我借助大语言模型（LLM）辅助，快速编写了一套 Python 数据处理脚本，构建了完整的数据预处理流水线：
智能乱码过滤：针对串口偶尔因为波特率抖动或中断阻塞产生的乱码字符（如 ♠HX)♣ 等），通过字符白名单机制（all(c in "0123456789,- " for c in line)）进行精准清洗，剔除异常行，保证数据纯净度。
多文件批处理与滑动窗口切分：利用 os 模块遍历原始导出的多个 .txt 长文本，按照固定大小（200 行，约 2 秒时长）进行滑动窗口切分。
Edge Impulse 格式对齐：在切分的同时，自动为每一行数据注入递增的 timestamp 时间戳（步长 10ms），并加上 accX, accY, accZ 的表头，一键生成完全符合 Edge Impulse 上传规范的标准 CSV 文件。极大地节省了手动切分数据的时间，将数据预处理效率提升了数十倍。

## 5. 模型训练、部署评估与工程决策 (TinyML)
模型训练：基于 Edge Impulse 提取加速度频域特征，训练全连接神经网络，模型验证集准确率达 88.2%。
初期的盲目乐观：在 Edge Impulse 平台上导出 int8 量化模型时，看到模型本身仅占用十几 KB 的 Flash 空间，原以为凭借 F103 的 64KB Flash 足以轻松应对。
深水区的现实打击：在实际尝试集成 TFLite Micro 引擎时，才发现底层生态的庞大。在 Keil 中手动排查大量的 .cc/.cpp 混合编译冲突、修复 CMSIS-NN 版本依赖差异，甚至在借助 DeepSeek Harness 辅助编写和梳理复杂底层依赖代码后，系统体积依然迅速逼近并突破了 F103 的极限。
性能与工程决策（果断止损）：经过严谨评估，F103 (Cortex-M3) 既无硬件 FPU（浮点运算单元），更缺乏 DSP/NPU 等 AI 向量加速指令。即便通过极限压缩将代码勉强塞进 64KB Flash，纯软件跑推理的延迟和内存开销也毫无实际应用价值。
最终方案：为了不陷入无意义的工具链内耗，果断停止在 F103 上的强行部署。结合现有需求，将后续的 TinyML 硬件目标转向自带向量指令扩展与更大内存（PSRAM）的 ESP32-S3，以构建真正具备实用价值的端侧 AI 系统。
